# 設計メモ：将来の移行を見据えて

このアプリは、次のように段階的に育てることを前提に作っています。

```
段階1 かんたん版      段階2 Google版          段階3 アプリ化             段階4 本格版
GitHub Pages     →   スプレッドシート   →   同じ画面をアプリに包む  →  独自のデータベース
端末に保存            ＋GAS＋Discord          （Capacitorなど）          独自AI・プッシュ通知
      └──── いま（v0.1）────┘
```

## 移行しやすくするための8つの決まりと、今の実装

| # | 決まり | 今の実装 |
|---|---|---|
| 1 | データの形を、保存先とは別の「定義書」として持つ | `src/schema.json`。画面の入力欄・シートの列・定義書（md）はすべてここから作る |
| 2 | すべての記録に固有のIDと更新日時を付ける | 共通の項目 `id` / `createdAt` / `updatedAt` / `deleted`。削除も印を付けるだけ（同期のため） |
| 3 | データの読み書きを1か所にまとめる | `app.js` の保存アダプタ（`createLocalStore` / `createGasStore`）。画面はアダプタの中身を知らない |
| 4 | AIを呼び出す部分を1か所にまとめる | v0.1ではAIを使っていない。追加するときは保存アダプタと同じ形で「AIアダプタ」を作る（下記） |
| 5 | 手続きの型やAIへの指示文はデータとして置く | `src/templates.json` |
| 6 | 表の形を崩さない（1行1件、結合なし） | GASはこの形でしか書かない。手で足した列は消さずに残す |
| 7 | 全データの書き出しを正式な形式にする | `task-a-remind-export` 形式（定義書の末尾）。`migrate()` で古い形式を変換。第2版（v0.2.0）で実際に使用：分類名の変更などを `upgradeCollections()` で自動変換 |
| 8 | 項目ごとに「見せてよい範囲」を付ける | `visibility`（誰に見せてもよい／支援者まで／家族のみ）。支援者向けの印刷はこれで絞っている |

## 保存アダプタの約束

```js
{
  kind, label,
  loadAll()            // → { children: [...], tasks: [...], ... }
  putMany([{col, rec}]) // IDが同じなら上書き、なければ追加
  getSettings() / saveSettings(obj)
  // あれば使う： saveFile(name, content, mime) / savePdf(html, name) / testNotify()
}
```

**Googleドライブ同期（v0.3.0）**は、保存アダプタは端末（localStorage）のまま、その上に同期（`src/drive-sync.js`）を重ねる形にしました。オフラインでも使えることを優先し、「取得 → 結合（`mergeImport`：更新日時の新しい方）→ 保存」を保存のたびに行います。削除は `deleted` の印で伝わります。

本格版では `createApiStore(baseUrl, token)` を追加し、同じ約束で独自サーバーのAPIを呼ぶだけで、画面はそのまま使えます。

## 共通ロジック（`src/logic.js`）

画面（DOM）にも保存先にも依存しない処理だけを置いています。ブラウザとGASの両方で同じファイルを使っています（GASには `Shared.gs` として埋め込み）。本格版のサーバー（Node.jsなど）でもそのまま使えます。

- 工程の逆算（`planProcess`）、今やれるかの判定（`isActionable`）、今日の集計（`summarize`）
- 通知の文面（`buildDigestText` / `buildDayText`）：医療の情報は載せない
- 書き出し・読み込み・移行（`makeExport` / `mergeImport` / `migrate`）

## 次に足すとよいもの（優先順）

1. **かんたん版の画面からGoogle版のデータを使う**（`createRemoteGasStore`）：GAS側に `doPost` の窓口を作り、GitHub Pagesの画面から読み書きする。利用者は「Webアプリの公開」をしなくてよくなる代わりに、合言葉（トークン）の管理が必要
2. **写真の添付**：Google版はドライブに保存してリンクを `photoUrl` に入れる。かんたん版はIndexedDBに縮小して保存
3. **AIによる書類の読み取り**（下記）
4. **施設シートの書き写しモード**：用紙の写真と「データを書き出す」の中身をAIに渡し、欄ごとの記入内容を出してもらう

## AIを足すときの注意（Gemini APIの場合）

Gemini APIの**無料枠**の利用規約では、入力内容が品質改善のために人に読まれることがあり、**機微な情報・個人情報を送らないよう**明記されています。

| 使い道 | 個人情報 | 方針 |
|---|---|---|
| 自治体ページの要約、手続きの型の下書き | 含まない | 無料枠でよい |
| 書類の写真から子どもの情報を読み取る | 含む | 有料枠（従量課金）にする、または利用者が自分でAIアプリに貼る「コピペ方式」にする |

どちらの場合も、AIが読み取った内容は**必ず確認画面を通してから**保存します（薬の量・アレルギーなどの読み違いを防ぐため）。

AIアダプタの形の案：

```js
{
  extract(imageOrText, targetCollections) // → [{col, rec}] の下書き（まだ保存しない）
  summarizePage(url)                      // → 出典つきの要約
}
```

## 段階4（本格版）に進むときに変わること

技術よりも、**データを預かる責任**が大きく変わります。段階3までは、データは各家庭の端末・Googleアカウントの中にあり、開発側は何も持っていません。独自のデータベースに移ると、開発側が要配慮個人情報を預かる立場になり、同意の取得・セキュリティ・費用・運用の体制が必要になります。
